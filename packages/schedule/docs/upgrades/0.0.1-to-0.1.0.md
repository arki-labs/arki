# Upgrading schedule outcomes

1. Keep each definition's inferred type. For a typed context, use
   `initSchedule.context<Context>().create().define(...)`. Avoid annotating a
   concrete definition with an erased `ScheduleDef` type or supplying only the
   first generic parameter to `defineSchedule`.
2. Handle `refused` separately from `ran`. Only `ran.value` is a successful
   handler value; `refused.failure` retains the original domain failure. The
   client derives names, successful values and failures from the definitions.
3. Handle canonical `UnexpectedDefect` in `handler-failed.cause`. Known lock
   store/lost failures use `ScheduleLockFailed`; an unknown lock exception is a
   defect with a private cause. Overlap, lock contention, unknown schedule names
   and stopped runtimes remain distinct scheduling outcomes.
4. Update durable adapters to consume the canonical schedule port. A completed
   tick delivery does not make a refused handler successful. The BullMQ adapter
   ships in `@arki/queue`; it preserves refusal details for operators.
5. Keep explicit cron response policies for domain outcomes that need a special
   HTTP response. Existing `respond` mappings receive domain refusals as well as
   successful values. An unmapped refusal uses the failure policy.
6. Remove surrounding whitespace from schedule names. Runtime names must match
   the literal names used for inference and inspection.

Schedule spans and duration measurements use the application's OpenTelemetry
provider. Handlers can add events to the active span; the package never configures
an SDK or exporter. Existing durable registration starts asynchronously, so a
registration log is not proof of backend readiness.

External effects remain at least once. Use idempotency keys, and compose Journal
when the operation must resume persisted steps after a restart.
