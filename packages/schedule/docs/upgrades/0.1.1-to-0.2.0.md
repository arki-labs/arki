# Upgrade @arki/schedule 0.1.1 to 0.2.0

You must act only if a dashboard, alert or trace query expects a scheduled run (`schedule.run` from an `every` timer, a cron tick or a durable fire) to sit under the app start span; everyone else can skip it.

## What changed

- A schedule tick now starts its own trace. Before, an `every` timer, a cron tick or a durable fire started `schedule.run` under whatever span was active when the app armed it. In a Dot app that was the `dot.unit.start` span, which had already ended, so every background run showed up as part of app startup. Now `schedule.run` for those ticks has no parent. `trigger(name)` still nests under the caller's span.
  
  Docs: README `## Observability`.

## Public API changes

No public API changes.

## Steps

1. Upgrade `@arki/schedule`. No code changes are needed.

2. Find trace queries that join a scheduled run to app startup. A tick now starts its own trace, so `schedule.run` has no parent and is no longer under `dot.unit.start`. Query it by span name `schedule.run` and the `schedule.name` attribute instead.

   Before:

   ```ts skip="before: the 0.1.1 trace shape"
   // schedule.run was a child of dot.unit.start
   const startupRuns = spans.filter((span) => span.parent?.name === 'dot.unit.start');
   ```

   After:

   ```ts skip="the 0.2.0 trace shape"
   // schedule.run is a root span for timer, cron and durable ticks
   const tickRuns = spans.filter((span) => span.name === 'schedule.run' && span.parent === undefined);
   ```

   A `trigger(name)` call still nests under the caller's span.


## Verify

```sh
bun run test
```

Run it in your app. It passes when no test or check still expects a scheduled tick under the startup span.
