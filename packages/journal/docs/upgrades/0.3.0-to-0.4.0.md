# Upgrade @arki/journal 0.3.0 to 0.4.0

0.4.0 adds durable workflows (README, Workflows). The breaking changes below were already in the 0.3.0 code, but its changelog did not list them. 0.3.0 was not published to npm, so an app on 0.2.1 should read the [0.2.1 to 0.3.0 guide](0.2.1-to-0.3.0.md) first, then this one.

## Steps

1. Pass the tables to `initJournal`, and take them out of `compose`.
2. Move `retention` from `compose` to `initJournal`.
3. In a Dot app, drop `tables` from `journal({ j })`.
4. Export the new tables and generate the migration. Migrate first, then roll the workers.
5. Check code that moves jobs by hand, retry rules on effects and steps, and code that read the unreleased workflow events.
6. Backfill `args` on pending effect jobs, or drain them, before the new check constraint.
7. Generate the migration for the `journal_jobs` changes that come with `events: 'transient'`: the check no longer needs `event_seq`, and a partial unique index is new.
8. Move each projection cursor from `seq` to `position` with the SQL in step 8, not the generated drop and add.
9. Generate the migration for the forward jobs: two new columns on `journal_jobs` and `journal_job_archive`, a third branch in the kind check, and a unique index.
10. Import the stored-value schemas from `@arki/journal/zod` under their new names.

## 1. `initJournal` takes the tables

The journal's own entities (a workflow run is one) are declared on the tables, like every app entity. So `initJournal` needs them, and `compose` no longer takes them.

Before:

```ts skip="before: the 0.2.1 API, which no longer compiles"
export const j = initJournal({ meta: z.object({ actorId: z.string() }) });
export const journal = j.compose({ tables, effects: [orderMail], services: { mailer } });
```

After:

```ts
import { z } from 'zod';

import { initJournal } from '@arki/journal';
import { journalTables } from '@arki/journal/pg';

export const tables = journalTables();
export const j = initJournal({ tables, meta: z.object({ actorId: z.string() }) });
export const journal = j.compose({ effects: [] });
```

The setup chain takes them the same way: `initJournal.tx<AppTx>().db<AppDb>().create({ tables, meta })`.

## 2. `retention` moves to `initJournal`

One policy now covers finished jobs and finished workflow runs, and the workflow timers read it before any `compose`. It gains `retention.workflows`.

Before:

```ts skip="before: the 0.2.1 API, which no longer compiles"
export const journal = j.compose({ tables, effects, retention: { archive: { completed: '7d' } } });
```

After:

```ts
import { initJournal } from '@arki/journal';
import { journalTables } from '@arki/journal/pg';

export const j = initJournal({
  tables: journalTables(),
  retention: { archive: { completed: '7d' }, workflows: { completed: '30d' } },
});
export const journal = j.compose({});
```

## 3. Dot: `journal({ j })`

Before:

```ts skip="before: the 0.2.1 API, which no longer compiles"
defineApp('shop')
  .use(db())
  .use(journal({ j, tables: journalTables() }));
```

After:

```ts skip="fragment: needs the app's database plugin and features"
defineApp('shop')
  .use(db())
  .use(journal({ j, workflowMeta: { actorId: 'system:workflow' } }));
```

`workflowMeta` is needed only when a feature declares workflows.

## 4. The migration

Three tables are new: `workflow_runs`, `workflow_steps` and `workflow_signals`. `journal_jobs` and `journal_job_archive` gain a nullable `run_id` column with an index. Every statement is additive.

Export each table on its own from the schema module, where drizzle-kit looks. `ExportsEveryJournalTable<typeof thisModule>` from `@arki/journal/pg` stops compiling and names any table you missed.

```ts
import { journalTables } from '@arki/journal/pg';

// The app's schema module: every journal table as its own top-level export.
export const {
  events,
  jobs,
  jobAttempts,
  jobArchive,
  jobOperations,
  receipts,
  cursors,
  workflowRuns, // new
  workflowSteps, // new
  workflowSignals, // new
} = journalTables();
```

```sh
drizzle-kit generate
```

Apply the migration, then roll the workers. A 0.2.1 worker runs on the new schema. A new worker on the old schema does not.

## 5. Behaviour changes

- `journal.retry`, `journal.discard` and `journal.cancel` throw `JOB_MANAGED` for a job with a `run_id`. Only workflow jobs have one, so no existing job is affected. Move workflow jobs with `journal.workflows.retryStep` and the other workflow verbs.
- An effect whose lease ran out, because another worker took the job, gets `LEASE_LOST` from `ctx.run`, and the command writes nothing. Before, the stale worker's command committed next to the new owner's. Make outside calls idempotent with `jobId`; that rule is unchanged.
- `EffectSchedule.when(event)` is new. An effect with it makes jobs only for the events it accepts.
- An error that an effect handler or a workflow step throws is retried by its `retry`, or by the default (8 tries, 1 s up to 5 minutes), the same rule as `@arki/queue`. `lastError` and the step's error record it as `UnexpectedDefect`. The `while` gets the error that was thrown, as is, not the defect: `.while(reason => reason instanceof TransientError)`. A predicate that dug the error out of the defect (`UnexpectedDefect.is(reason)`, `reason.cause`, `findCause`) now tests the error directly. A returned failure is dead at once, unless the `while` accepts it.

For code written against the unreleased workflow code in 0.3.0:

- `NodeSkipped` event data has a required `cause`: `when`, `compensating`, `no-undo`, `detached` or `operator`. `reason` stays the text for people.
- A node dropped by compensation (a wait the run was parked on) leaves no key in `results`. It used to be `null`. `def.read` types results as optional for this reason.
- `RunDetail` takes `<Input, Output, Results>`, and `WorkflowDef`, `WorkflowStarter`, `DefExtension` and `ApplyExtension` have new type parameters. Code that names these types without arguments still compiles. Prefer the inferred types: `def.read` returns a typed `RunDetail`.
- `finish(fn)` with a declared `output` compiles with one argument.
- `compose({ workflows })` checks each workflow's needs against `services` at compile time, as it does an effect's. A list typed as plain `WorkflowDef[]` may need anything, so `compose` then asks for `services`; keep the inferred definition types instead.
- `Effect.bindPerWorkflow` is internal and gone from the published types.

## 6. Effect jobs carry their event

Every effect job now holds a copy of its `journal_events` row in `journal_jobs.args`. The worker, `journal.job` and the workflow runner read the event from that copy and never join `journal_events`. `journal_jobs_kind_check` changes: an effect row must have `args`. `event_seq` and `unique (event_seq, effect)` stay.

The migration from `drizzle-kit generate` replaces the check. It fails while a pending effect job has no `args`. Before it, either drain the workers until `journal_jobs` holds no effect row, or backfill the copy. The keys are the Drizzle property names, as the writer stores them:

```sql
update journal_jobs as job
set args = jsonb_build_object(
  'seq', stored.seq, 'id', stored.id, 'kind', stored.kind, 'entityId', stored.entity_id,
  'version', stored.version, 'type', stored.type, 'data', stored.data, 'meta', stored.meta,
  'recordedAt', stored.recorded_at, 'commandId', stored.command_id, 'causeSeq', stored.cause_seq,
  'correlationId', stored.correlation_id, 'erasedAt', stored.erased_at, 'schemaVersion', stored.schema_version)
from journal_events as stored
where job.kind = 'effect' and job.args is null and stored.seq = job.event_seq;
```

Run the same statement on `journal_job_archive` if a replay of an archived effect job must still work: `replay` copies `args`, and the new check refuses a copy without it. Archived rows without a copy are otherwise left alone; they have no event data for `forget` to erase.

After the migration, `forget` also rewrites the copy in `journal_jobs` and `journal_job_archive`. The archive holds event data for as long as `retention.archive` keeps the job (7 days by default).

## 7. Effect rows without an event row

0.4.0 adds `events: 'stored' | 'transient'` on `initJournal` and `j.entity` (README, Transient events). An effect job for a transient entity's event has no `journal_events` row to point at, so `journal_jobs_kind_check` now requires `effect` and `args` on an effect row and leaves `event_seq` optional. The new partial unique index `journal_jobs_effect_event_id_unique` on `((args->>'id'), effect) where kind = 'effect'` keeps one job per event and effect for those rows, as `unique (event_seq, effect)` does for stored events; an archive replay cannot double-run them.

An entity switched from `'transient'` to `'stored'` later: change the setting, then `journal.adopt` each row before its first write. `adopt` now takes a row at any version whose log is empty; the row keeps its values, its create event is version 1, and its version becomes 1.

`drizzle-kit generate` produces both statements. They are additive: no backfill, no data change. The index can only fail to build if two live effect rows share an event id and effect, which `unique (event_seq, effect)` already prevented for every row that has a `seq`. Nothing changes for an app that never sets `events`.

## 8. Projection cursors are log positions

An async projection's cursor is now a position in the event log, not a `seq` number: `journal_cursors.seq` (bigint, default 0) becomes `journal_cursors.position` (text, null at the start). The built-in log writes a seq as text, so the values carry over. The column is generic so a later event log with its own order can use it.

`drizzle-kit generate` drops `seq` and adds `position`. Run this instead, so no cursor goes back to the start. A cursor at the start re-applies every event to its read model.

```sql
alter table journal_cursors add column position text;
update journal_cursors set position = case when seq = 0 then null else seq::text end;
alter table journal_cursors drop column seq;
```

With `journalTables(schema)`, the table is `<schema>.journal_cursors`.

Two API changes come with it:

- `journal.cursors(db)` returns `{ name, position, behind, distance }`. `behind` is true while the log holds events after `position`. `distance` is how many seqs behind it is; it replaces `lag`. Wait for `behind: false` where you waited for `lag: 0`.
- `journal.rerun(db, projection, { after })` takes a position (`EventLogPosition`, or `null` for the start) instead of `afterSeq`.

## 9. Forward jobs and job streams

0.4.0 lets `events` name an event log outside the app database (README, Events in another store). Its events travel in a new job kind, `forward`. `drizzle-kit generate` produces every statement, and all of them are additive:

- `journal_jobs.stream` (varchar) and `journal_jobs.stream_position` (integer), both null on every existing row. A check keeps them null or set together.
- `journal_jobs_stream_position_unique`, a unique index on `(stream, stream_position)` where `stream` is set.
- `journal_jobs_kind_check` gains a third branch: a `forward` row has `job_name` (the entity kind), `args`, `stream` and `stream_position`, and no `event_seq`, `effect` or `dedupe_key`.
- The same two columns on `journal_job_archive`, with an index on `stream`.

Existing rows keep passing the check, and an app that never passes a log writes no forward job. Foreman's job module lists `forward` as a third kind.

## 10. Schemas move to `@arki/journal/zod`

Public types no longer name Zod, so the schemas that decode stored values moved to their own entry and took the package's `xSchema` names. The types stay where they were.

| Before                                            | After                                             |
| ------------------------------------------------- | ------------------------------------------------- |
| `StoredEventRow` (schema) from `@arki/journal/pg` | `storedEventRowSchema` from `@arki/journal/zod`   |
| `ForwardArgs` (schema) from `@arki/journal/pg`    | `forwardArgsSchema` from `@arki/journal/zod`      |
| `EventLogPosition` (schema) from `@arki/journal`  | `eventLogPositionSchema` from `@arki/journal/zod` |

`@arki/journal/foreman` drops its four summary schemas (`AttemptSummary`, `OperationSummary`, `ArchivedSummary`, `JobSummary`). The types keep their names. `journalJobsModule` and `journalWorkflowsModule` now return a plain `ForemanModule` from `@arki/admin`: register them as before. Code that called a read on the returned object directly gets `unknown` results now; parse them, or go through the admin dispatcher.

`EventLogPosition` is still exported from `@arki/journal`, as a type only. It is a TypeScript brand now, and `eventLogPositionSchema` is the one way to make one: `parse(eventLogPositionSchema, text)` from `@arki/schema` for text from outside, or `ensure` for a position you know is valid.
