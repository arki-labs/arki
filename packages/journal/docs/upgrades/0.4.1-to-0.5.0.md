# Upgrade @arki/journal 0.4.1 to 0.5.0

You must act if you call `subscribe`, `dispatch`, `replay`, `rotateSecret`, `enable` or `disable` on the webhook sender, use `WebhookError` or `WEBHOOK_ERROR_CODES`, call `checkEventMapFile`, or start a worker with a `listen`; everyone else can skip it.

## What changed

- `checkEventMapFile` returns an `EventMapFileFailed` failure (`journal.event_map_file_failed`) instead of rejecting when the file cannot be written, and no longer reports an unreadable file as `missing`: only "no such file" is `missing`. `scanEntrypoints` records a procedure file it cannot read (a broken symlink, no permission) as a `problems` entry and scans the rest.
- `SubscribeInput` and `DispatchInput` in `@arki/journal/http/webhooks` are now plain TS types (same shape), and their schemas are internal, so the entry names no Zod type.
- The webhook sender returns failures for outside input instead of throwing `WebhookError`.
  
  - `subscribe` returns `InvalidInput` (`schema.invalid_input`) when its input fails the schema or the URL is not public https. The issues name the field (`url`, `events`, ...).
  - `dispatch` returns `InvalidInput` for input that fails its schema or a payload that is not JSON (a bigint, a cycle), and `journal.webhook_payload_too_large` for a body over `maxPayloadBytes`. Nothing is written for either.
  - `replay` returns `journal.webhook_not_found` for an unknown message or subscription and `journal.webhook_other_partner` for a subscription of another partner. `rotateSecret`, `enable` and `disable` return `journal.webhook_not_found` for an unknown id.
  - A wrong `encryptionKey` throws `journal.webhook_configuration_invalid` (as `UnexpectedFailure`) when `webhookSender(...)` is built. `dispatch` given the root database throws `invariant` (a caller bug). A non-2xx answer is recorded as `journal.webhook_delivery_failed` and retried by the worker as before.
  - `WebhookError` and `WEBHOOK_ERROR_CODES` are removed. `SubscribeInput` and `DispatchInput` are now read from their schemas; their shape is unchanged.
  - `journalReceiptStore` (`@arki/journal/foreman`): a claim that loses the insert to a writer outside the journal's append lock now answers `{ claimed: false, receipt }` with the stored receipt. Before, it threw `UnexpectedFailure`.
  
  Upgrade: check the result of `subscribe`, `dispatch`, `replay`, `rotateSecret`, `enable` and `disable` with `isFailure`, or wrap them in `orThrow(...)` where a failure is a bug. Replace `WEBHOOK_ERROR_CODES` matches with the failure codes above.
- Each job the worker runs now starts its own trace. Before, a worker started inside Dot's start hook put every `journal.effect` span (and the `journal.step` and command spans under it) under the `dot.unit.start` span, which had already ended, so background jobs looked like part of app startup. The worker's loops, its sweeper and its tap dispatch now run in the root context. Journal rows carry no OpenTelemetry context, so there is no producer trace to continue.
  
  Docs: README `## Observability`.
- A Postgres listener that cannot start now returns its failure instead of rejecting.
  
  - `@arki/db`: `listenOnPool(pool, channel)(onMessage)` resolves to `ListenUnavailable` (`db.listen_unavailable`) when the first connection or `LISTEN` fails. It no longer rejects with an `UnexpectedFailure`. The raw pool error stays its private `cause`. Nothing retries: call the start again.
  - `@arki/journal`: a `WakeListener` may return a `Failure`. `worker.start()` resolves to that failure and leaves the worker stopped, so a later `start()` tries again. A `listen` that throws also leaves it stopped (before, the worker stayed marked running and every later `start()` did nothing). The failure type is inferred: a worker without `listen` returns no failure. In Dot, `journalWorker()` returns the failure from `start`, so the app's start fails with it.
  - `@arki/pubsub`: `PubSub` and `TransactionalPubSub` take a `SubscribeFailure` type (`never` by default). `pgPubSub`'s `subscribe` resolves to `db.listen_unavailable` when the channel's listener cannot start; nothing stays subscribed, and the next `subscribe` tries again.
  - `@arki/live`: a `LiveSource`'s `start` may return a failure, and `hub.start()` resolves to it (`pgSource`: `db.listen_unavailable`). The hub stays `idle` and stopped, so a later `hub.start()` on the same hub tries again; a successful start happens once. `liveQueries()` returns it from its Dot `start`.
  
  Upgrade: check the result of `worker.start()`, `hub.start()` and pg `subscribe()` where a listener is wired, for example `orThrow(await worker.start())` in a script, or return it from a Dot `start` hook.

## Steps

1. Upgrade `@arki/journal` to 0.5.0. If you use `@arki/db` or `@arki/live`, upgrade them too: they ship in the same release. The `@arki/pubsub` change ships in a later release.

2. Check the result of each webhook sender call with `isFailure`. These calls return failures for bad input and unknown ids. They no longer throw `WebhookError`.

   Before:

   ```ts skip="fragment: upgrade before and after snippet"
   try {
     await webhooks.dispatch(tx, { partner: tenantId, event: 'order.placed', payload: { orderId } });
   } catch (error) {
     if (error instanceof WebhookError && error.code === WEBHOOK_ERROR_CODES.PAYLOAD_TOO_LARGE) retryLater();
   }
   ```

   After:

   ```ts skip="fragment: upgrade before and after snippet"
   const result = await webhooks.dispatch(tx, { partner: tenantId, event: 'order.placed', payload: { orderId } });
   if (WebhookPayloadTooLarge.is(result)) retryLater();
   ```

   Where a failure is a bug, wrap the call: `orThrow(await webhooks.dispatch(tx, input))`. Import `WebhookPayloadTooLarge`, `WebhookNotFound` and `WebhookOtherPartner` from `@arki/journal/http/webhooks`.

3. Remove `WebhookError` and `WEBHOOK_ERROR_CODES`. Match the failure codes instead: `journal.webhook_payload_too_large`, `journal.webhook_not_found`, `journal.webhook_other_partner` and `schema.invalid_input`.

4. Check the result of `checkEventMapFile`. It returns `EventMapFileFailed` when it cannot write the file.

   Before:

   ```ts skip="fragment: upgrade before and after snippet"
   const check = await checkEventMapFile({ file, mermaid });
   ```

   After:

   ```ts skip="fragment: upgrade before and after snippet"
   const check = orThrow(await checkEventMapFile({ file, mermaid }));
   ```

5. Check the result of `worker.start()` where the worker has a `listen`. It resolves to the failure and the worker stays stopped. A later `start()` tries again. In a Dot app, `journalWorker()` returns it from `start` and you need no change.

   Before:

   ```ts skip="fragment: upgrade before and after snippet"
   await worker.start();
   ```

   After:

   ```ts skip="fragment: upgrade before and after snippet"
   orThrow(await worker.start());
   ```
