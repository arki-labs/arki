# Upgrade @arki/kv 0.4.0 to 0.5.0

Act on this if you call `get`, `mget`, `set`, `mset`, `delete` or any other data method of `KV` yourself, catch Redis errors from them, import `RateLimitExceededError`, or run your own store on `KV` (`@arki/admin`, `@arki/embeddings`, `@arki/geo`, `@arki/mail` already follow). Apps that only mount `kv()` and use the other `@arki` packages through it can skip the steps.

## What changed

- `@arki/kv` data methods return typed failures instead of rejecting with the raw Redis error. `get` and `mget` take a schema (any Standard Schema) and return the checked value, `undefined` for a missing key, or `KvValueInvalid`. Every method returns `KvUnavailable` when Redis is down, slow (`commandTimeoutMs`, default 5000) or drops the reply, and `KvCancelled` when the `signal` option aborts; after a failed write the effect is unknown. `mset` now applies its TTL, and `setIfNotExists` writes the same stored format as `set`, so `get` reads it back. `close()` returns `KvCloseFailed` instead of logging to the console. TLS certificates for a `rediss://` URL are now verified; skipping the check needs `allowUnverifiedTls: true` (or `KV_ALLOW_UNVERIFIED_TLS`). A rate limiter made while Redis is not ready is listed in `degradedRateLimiters` and is rebuilt on Redis once the connection is ready. Every command runs under a `kv.<command>` span. The consumers follow: `@arki/admin` `ReceiptKV`, `@arki/embeddings` `kvCacheStore`, `@arki/geo` `GeocodingCache` and `@arki/mail` `QuotaStore`/`kvQuotaStore` take the new `get(key, schema)` and failure-returning methods; a cache or quota failure is logged and read as a miss.
  
  `@arki/kv` no longer exports `RateLimitExceededError`: nothing in kv threw it. `getRateLimiter(...).consume()` rejects with the limiter's own `RateLimiterRes`, which `@arki/kv` now re-exports; check it with `instanceof` and read `msBeforeNext`. `get` and `mget` now return a schema failure that is not a wrong shape (an async schema, a validator defect) as the failure itself; before, it was returned as if it were the stored value.

## Public API changes

Removed:

- `RateLimitExceededError` from `@arki/kv/errors`. Nothing in kv threw it.

Changed:

- `get(key, schema, options?)` and `mget(keys, schema, options?)` take a Standard Schema as the second argument. They return the checked value (`undefined` for a missing key), `KvValueInvalid` when the stored value has the wrong shape, or the schema's own failure when the schema cannot run (an async schema, a validator defect). Before, `get<T>(key)` returned the stored value cast to `T`, and a schema failure came back as if it were the value.
- `set`, `setIfNotExists`, `mset`, `exists`, `delete`, `deleteMany`, `clear` and `publish` return their old result or a `KvUnavailable` or `KvCancelled` failure. `mset` and `clear` return `undefined` on success. Before, they rejected with the raw Redis error.
- `mset` takes a read-only list of read-only pairs and applies its TTL to every pair. `setIfNotExists` writes the same stored format as `set`.
- `getRateLimiter(id, options).consume()` rejects with `RateLimiterRes`; a limiter made while Redis was not ready is rebuilt on Redis once it is ready.
- `close()` waits at most `commandTimeoutMs` for each disconnect.

Added:

- `KvUnavailable` (code `kv.unavailable`, status 503), `KvCancelled` (`kv.cancelled`, 499) and `KvValueInvalid` (`kv.value_invalid`, 500), exported from `@arki/kv`.
- `KvCallOptions` with `signal`, the last argument of every data method.
- `commandTimeoutMs` in `KvOptions` (default `5000`) and in the `kv()` Dot options.
- `RateLimiterRes`, re-exported from `@arki/kv`.
- `KV.degradedRateLimiters` and the `kv.<command>` spans, as in the 0.4.0 guide.

## Steps

1. Give every `get` and `mget` a schema. The result is the checked value, `undefined` for a missing key, or a failure. Check for the failure before you use the value.

   ```ts skip="before: the 0.4.0 API"
   const session = await kv.get<{ userId: string }>(`session:${token}`);
   const [first, second] = await kv.mget<string>(['a', 'b']);
   ```

   ```ts
   import { isFailure } from '@arki/failure';
   import { z } from '@arki/contracts';
   import type { KV } from '@arki/kv';

   const sessionSchema = z.object({ userId: z.string() });

   export async function userIdOf(kv: KV, token: string): Promise<string | undefined> {
     const session = await kv.get(`session:${token}`, sessionSchema);
     // A failure is `kv.unavailable` (Redis down or slow), `kv.cancelled`, or `kv.value_invalid` (wrong shape).
     if (isFailure(session)) throw session;
     return session?.userId;
   }

   export async function firstTwo(kv: KV): Promise<readonly (string | undefined)[]> {
     const values = await kv.mget(['a', 'b'], z.string());
     if (isFailure(values)) throw values;
     return values;
   }
   ```

2. Check the result of every write. A failed write means the effect is unknown: read the key before you assume it changed. Stop wrapping calls in `try` and `catch` for Redis errors; they no longer reject.

   ```ts skip="before: the 0.4.0 API"
   try {
     await kv.set('greeting', 'hello', 60);
   } catch (error) {
     logger.warn('set failed', { error });
   }
   ```

   ```ts
   import { isFailure } from '@arki/failure';
   import type { KV } from '@arki/kv';

   export async function saveGreeting(kv: KV): Promise<boolean> {
     const written = await kv.set('greeting', 'hello', 60);
     // `written` is `true` or `false` from Redis, or a `KvUnavailable` or `KvCancelled` failure.
     return !isFailure(written) && written;
   }
   ```

3. If you waited for ever on a dead Redis before, you now get `KvUnavailable` after `commandTimeoutMs` (default 5000 ms). Pass a `signal` to stop a call earlier. It returns `KvCancelled`.

   ```ts
   import { isFailure } from '@arki/failure';
   import { KvCancelled, type KV } from '@arki/kv';

   export async function removeKey(kv: KV, key: string, signal: AbortSignal): Promise<string> {
     const deleted = await kv.delete(key, { signal });
     // A cancelled write may still have landed, so read the key before you assume.
     if (isFailure(deleted)) return KvCancelled.is(deleted) ? 'cancelled' : 'unavailable';
     return deleted ? 'deleted' : 'missing';
   }
   ```

4. Replace `RateLimitExceededError` with `RateLimiterRes`. `consume()` rejects with the limiter's own result, so check it with `instanceof` and read `msBeforeNext`.

   ```ts skip="before: the 0.4.0 API"
   import { RateLimitExceededError } from '@arki/kv/errors';

   if (error instanceof RateLimitExceededError) retryAfter(error.limiterResult.msBeforeNext);
   ```

   ```ts
   import { RateLimiterRes, type KV } from '@arki/kv';

   export async function allowRequest(kv: KV, ip: string): Promise<number | undefined> {
     const limiter = kv.getRateLimiter('login', { points: 5, duration: 60 });
     try {
       await limiter.consume(ip);
       return undefined;
     } catch (error) {
       if (error instanceof RateLimiterRes) return error.msBeforeNext;
       throw error;
     }
   }
   ```

5. If you wrote your own cache or store on `KV` and passed it to `@arki/admin`, `@arki/embeddings`, `@arki/geo` or `@arki/mail`, give it the same shape: `get(key, schema)` and methods that return failures. A failure from the cache or quota store is logged and read as a miss.

## Verify

```sh
bun run typecheck
```

Run it in your app. It must pass with no errors. A `get` call without a schema, or an import of `RateLimitExceededError`, shows here as a type error.
