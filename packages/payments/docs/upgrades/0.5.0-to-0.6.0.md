# Upgrade @arki/payments 0.5.0 to 0.6.0

You must act if you call `DunningCampaignService.deleteCampaign`, `TaxExemptionRepository.updateExemption`, a tax repository write, `deleteJurisdiction`, `generateComplianceReport`, `exportTaxData`, `createAuditEntry`, or build `RefundService` with a `NotificationService`, or `DunningExecutionRepository.incrementRetryCount`, or if a dashboard groups on the span attribute `payments.failure_code`. Dunning apps must also act if they build `DunningCampaignRepository` or `DunningTemplateRepository`, call `DunningTemplateRepository.create` or `delete`, `DunningExecutionRepository.create`, `DunningCommunicationRepository.create`, `executeCampaign`, `CustomerRiskProfileRepository.create` or `upsert`, or store more than one risk profile per customer.

## What changed

- `deleteCampaign` returns `DunningTemplateInUse` (`payments.dunning_template_in_use`, 409) for a campaign whose step already sent a communication. It used to throw the database's foreign-key error. Nothing is deleted. It returns `undefined` when it deletes.
- `updateExemption` returns `InvalidInput` (`schema.invalid_input`) when the row the update leaves names no customer, product code or jurisdiction, or ends before it starts. It used to throw the table's CHECK error. Nothing is written. `createExemption` returns the same failure for an end before the start.
- `retryFailedExecutions` retries for real. An execution that throws is `failed` with a `nextRetryAt` of 30, 60, then 120 minutes. Each retry counts once in `retryCount`. After 3 retries it stays failed with no `nextRetryAt`.
- `DunningExecutionRepository.incrementRetryCount` is gone. `startRetry(id)` starts a retry (status `running`, `retryCount` plus one, no `nextRetryAt`). `recordFailure(id, errorMessage, nextRetryAt)` records a run that threw.
- A returned failure sets the span attribute `failure.code` instead of `payments.failure_code`.
- `DunningCampaignRepository.delete` returns `DunningTemplateInUse` like `deleteCampaign`, and its factory takes `dunningTemplates` and `dunningCommunications` too. `createDunningRepository` already passes them.
- `DunningTemplateRepository.create` returns `DunningCampaignNotFound` (`payments.dunning_campaign_not_found`, 404) for a `campaignId` with no campaign. It used to throw the database's foreign-key error.
- `DunningTemplateRepository.delete` returns `DunningTemplateInUse` for a step that already sent a communication, and its factory takes `dunningCommunications` too.
- `DunningExecutionRepository.create` returns `DunningCampaignNotFound`, `DunningTemplateNotFound` (`payments.dunning_template_not_found`, 404) or `ReferenceNotFound` (customer, subscription, payment) for a reference with no row; `executeCampaign` passes it on. `DunningCommunicationRepository.create` returns `DunningExecutionNotFound` (`payments.dunning_execution_not_found`, 404), `DunningTemplateNotFound` or `ReferenceNotFound` (customer); `sendCommunication` passes it on and sends nothing.
- `CustomerRiskProfileRepository.create` and `upsert` return `ReferenceNotFound` (`payments.reference_not_found`, `kind: 'customer'`) for an unknown customer, and never `undefined`. So do `updateCustomerRiskProfile` and the `DunningIntegrationService` event handlers that update the profile.
- `customer_risk_profiles` has a unique index on `customer_id` (`customer_risk_profiles_customer_id_idx`). `upsert` writes in one statement, so two first upserts at once leave one row.
- `handlePaymentSuccess` (and a subscription recovery) throws the database error when it cannot cancel an active execution. It used to log it and resolve.
- A notification provider that cannot be reached throws `PaymentProviderError` with code `unavailable` (retryable) instead of a plain `Error`. A `getDeliveryStatus` message id with a lone UTF-16 surrogate returns `schema.invalid_input`. When `sendCommunication` cannot mark the row failed after a thrown send, it throws an `AggregateError` of both errors, the send error first.
- The dunning contracts refuse text holding U+0000 (also in stored JSON) and `stepNumber`, `delayHours` and `updateFrequency` above 2^31 - 1, as `schema.invalid_input`. Postgres refuses both.
- The dunning contracts bound every span at 100 years: `cooldownPeriod` and `delayHours` at `MAX_DUNNING_HOURS` (876 000), the sum of a campaign's step delays too, the trigger day counts and the segment `lastPaymentDate.daysAgo` and `paymentFailureHistory.timeframe` at `MAX_DUNNING_DAYS` (36 500), and `subscriptionDuration` at 1 200 months. `updateCommunicationStatusInputSchema.providerMessageId` is at most 255 characters. A longer value is `schema.invalid_input`; before, it threw a raw `RangeError` or a Postgres error after the row was written.
- `communicationWebhookSchema` is now the shape `handleCommunicationWebhook` reads: `{ providerMessageId, event, timestamp, metadata? }` (it was `{ communicationId, event, timestamp, providerData? }`, which no method read; the `sent` event is gone). `handleCommunicationWebhook` parses its payload with it, returns `schema.invalid_input` for a payload it refuses, `DunningCommunicationNotFound` (`payments.dunning_communication_not_found`, 404) for an unknown provider message id, and the updated communication otherwise (it returned `void`).
- A scheduled execution whose message did not go out is `failed`, not `completed`, and is listed in the tick report: a thrown send (provider unreachable, database error) with `code: null` and a retry; a returned failure with its code, retried only for a 5xx `payments.notification_provider_rejected` (never for `payments.notification_provider_timeout`: the message may have gone out). `retryFailedCommunications` skips a communication whose execution is `failed` with a `nextRetryAt`, and one a later communication of the same execution replaced, so a message is resent by one job only. `createCommunicationOrchestrationService` and `new CommunicationOrchestrationService` take `dunningExecutions` beside `dunningCommunications`. `communicationsSent` and `customersReached` count only sent messages.
- `handlePaymentFailure`, `handleSubscriptionStatusChange` and `handleTrialEnding` throw a campaign run that threw instead of logging it and resolving. They return `ReferenceNotFound` for a customer, subscription or payment with no row (from `scheduleRetries` too; a payment with no subscription still only skips the retries). `handleTrialEnding` returns `HandlerFailure` and now runs `time_based` campaigns (it looked for a `trial_ending` trigger no campaign can have).
- Actor ids are `UserId` (`usr_...`): `createCampaign`, `updateCampaign`, `updateCampaignStatus`, `createSegment` and the repository `create`/`update`/`updateStatus` calls they use. An id Postgres cannot store returns `schema.invalid_input`. `findActiveCampaignsForTrigger` and `findActiveForTrigger` take the trigger type union and `CustomerSegmentId[]`; `findByRiskCategory` and `getCustomersByRiskCategory` take a `RiskCategory`.
- The execution and communication repository writes (`create`, `updateStatus`) and `CustomerSegmentRepository.updateCustomerCount` return `schema.invalid_input` for a value their column refuses. `recordFailure` stores `The error message cannot be stored` in place of a message Postgres cannot hold. `findByProviderMessageId` finds nothing for an id the column cannot hold.
- `CustomerRiskProfileRepository.create` returns `CustomerRiskProfileExists` (`payments.customer_risk_profile_exists`, 409) for a customer that has a profile (it threw a raw 23505).
- Provider answers are checked before they are stored: a Resend id or Twilio sid over 255 characters or holding U+0000 is `payments.notification_provider_response_invalid`; a provider error text holding U+0000 leaves `upstreamMessage` `null`. `sendCommunication` returns `schema.invalid_input` for a recipient the column cannot store, and sends nothing.
- Tax: every repository write checks its row and returns `schema.invalid_input` for a value its column refuses (U+0000, text over the `varchar` length, a bigint in JSON, a time outside the years 1 to 9999, a negative tax amount, a rate of 10000 or more) instead of a raw Postgres error. `createConfiguration`, `updateConfiguration`, `createJurisdiction`, `updateJurisdiction`, `approveExemption`, `TaxAuditRepository.record` and `TaxRecordRepository.recordMany` gain `SchemaFailure` in their results; `recordMany` returns `SchemaFailure | undefined` (it returned `void`). `createConfiguration`, `createJurisdiction`, `createExemption` and `record` return `TaxRowExists` (`payments.tax_row_exists`, 409) for a taken explicit `id`.
- `TaxJurisdictionRepository.deleteJurisdiction` returns `TaxJurisdictionInUse` (`payments.tax_jurisdiction_in_use`, 409) for a jurisdiction a child jurisdiction or an exemption names, and `undefined` when it deletes. Its constructor takes `{ taxJurisdictions, taxExemptions }`.
- `TaxService.calculateTax` and `createTaxTransaction` return `TaxLineCurrencyMismatch` (`payments.tax_line_currency_mismatch`, 422) for a line item in another currency than `currency`; `createTaxTransaction` returns `schema.invalid_input` for records it cannot store before Stripe is asked, and `TaxCurrencyMismatch` for a reference recorded earlier in another currency.
- `TaxReportingService.generateComplianceReport` and `exportTaxData` return `StoredTaxInvalid` (`other_currency`) for a tax record in another currency than its payment. `createAuditEntry` returns `schema.invalid_input` or `TaxRowExists`. `averageTaxRate` leaves out a payment whose tax equals its amount (it was `Infinity`).
- The refund commands return `CommandNotFound` (`journal.not_found`) for a user id with no user row, and `schema.invalid_input` for text holding U+0000.
- `RefundService` and `createRefundService` no longer take a `NotificationService`: the customer's rejection mail is the `refund-rejection-notice` effect of `createRefundEffects`. The approval and rejection effects return a mail failure (it was logged and acked): `payments.notification_failed` is retried with backoff, any other failure makes the job dead at once with it as `lastError`. The `payments.refund` workflow output has `notificationFailure` when its last mail did not go out.
- Core journal commands look up and lock the rows a write points at. `initiatePayment`, `createSubscription`, `syncSubscription` and `changeSubscriptionPlan` return `ReferenceNotFound` (`payments.reference_not_found`, with `kind` `user`, `customer`, `plan` or `subscription`) for an id with no row; they used to return `db.transaction_rejected` (SQLSTATE 23503). `ReferenceNotFound` has the new kind `user`. `createSubscription` returns `journal.conflict` for a provider subscription id that is already stored (it was `db.transaction_defect`). `markSubscriptionPastDue` returns `journal.conflict` for a canceled subscription (it moved it to `past_due`).
- The core command schemas, the contracts in `core/contracts` and the insert schemas of `createCoreDerivedSchemas` refuse what a column refuses, as `schema.invalid_input`: U+0000 or a `bigint` in text or JSON, text past its `varchar` length, a fractional `limit`, `offset`, interval count or trial length, a currency outside ISO 4217, an amount past 2^53 - 1 minor units (`nonNegativeMoneySchema`), and a time outside the years 1 to 9999. The derived plan insert schema accepts a free plan (price 0), and no derived insert schema fills a default any more (the column does).
- `PaymentRepository` writes check their input against the columns and return `schema.invalid_input` instead of a raw Postgres error. `createPlan` returns `PlanAlreadyExists` (`payments.plan_already_exists`, 409) for a taken id. `createCustomer` and `updateCustomer` return `ReferenceNotFound` (kind `user`); `updateCustomer` returns `CustomerConflict` for a user or provider customer another customer holds. `deleteCustomer` returns `CustomerInUse` (`payments.customer_in_use`, 409) while a refund points at one of its payments, and `undefined` otherwise. `createWebhookEvent` and `updateWebhookEvent` return `WebhookEventExists` (`payments.webhook_event_exists`, 409); `claimWebhookEvent`, `updateWebhookEvent` and `incrementWebhookEventAttempts` can return `schema.invalid_input`.
- `PaymentRepository` reads: a lookup by a provider id no column can hold returns `null`. A time outside the years 1 to 9999, or a fractional count, throws an invariant failure (a stated precondition). `findSubscriptionsEndingInRange` takes an optional `status` (default `active`); `findUnprocessedWebhookEvents` takes an optional `belowAttempts`; `findWebhookEventsCreatedBetween` is new.
- `WebhookHandler.processWebhook` returns `payments.webhook_payload_invalid` for a body holding U+0000 or an event id past 255 characters, and stores a source address longer than 45 characters as `null`. `retryFailedWebhooks` reads only events with attempts left, and emits `webhook:failed` once, when the last attempt fails; it no longer overwrites the stored error with `Max retry attempts exceeded`.
- `DunningService.processDunningEvents` returns one report per step it ran (`done`, `refused` with the failure, or `thrown`; it returned nothing). A refused provider pause, cancel or retry, or a refused journal write, is now `refused` instead of only a log line. `handlePaymentFailure` marks the subscription `past_due` first and schedules nothing when that write is refused.
- `ProrationService.previewMultiplePlanChanges` returns `{ previews, refused }` (it returned the previews alone and logged the refused plans), or `ReferenceNotFound` for an unknown subscription.
- `SubscriptionManager.handleTrialEndingSoon` finds trialing subscriptions (it always returned `[]`) and throws for a day count that is not a whole number from 0 to 365. `validateSubscriptionAccess` grants a `trialing` subscription, as `getEntitlement` does. `WebhookAnalyticsService` counts processed events. Each `PaymentRetryService` keeps its own copy of the retry strategies.
- `createSubscriptionBilling`: `handleWebhook` and `projectStripeSubscription` parse the subscription object and return `schema.invalid_input` for a body missing what they read. `createCheckoutSession` returns `schema.invalid_input` for an email past 255 characters before Stripe is asked, and passes on `ReferenceNotFound` from `createCustomer`.
- `PaymentMonitoringService.recordPaymentAttempt`, `recordRefund`, `recordSubscriptionEvent` and `recordWebhookProcessing` return the first KV failure (`kv.unavailable`, `kv.cancelled`) when a metric could not be stored, or `undefined`; they returned nothing and lost the failure. `StripeProvider.calculateTax` and `createTaxTransaction` return `money.provider_amount` for a currency outside ISO 4217 instead of throwing `UnknownCurrencyError`.

## How to upgrade

1. Branch on the result of `deleteCampaign` and `updateExemption`. An HTTP route answers with the failure's `status` (409 or 400).
2. Replace `incrementRetryCount(id)` with `startRetry(id)`, and `incrementRetryCount(id, nextRetryAt)` after a failed run with `recordFailure(id, errorMessage, nextRetryAt)`.
3. Rows that `processScheduledExecutions` marked `failed` before this version have no `nextRetryAt`, so they are not retried. To retry them, set `next_retry_at` on those rows.
4. Group dashboards and alerts on `failure.code`.
5. Before you push the new schema, keep one row per customer in `customer_risk_profiles` (delete the older duplicates), or the unique index cannot be created.
6. Branch on the results of the dunning repository `create` and `delete` calls, the risk profile writes, `executeCampaign`, `sendCommunication` and the event handlers. Pass `dunningTemplates` and `dunningCommunications` to `createDunningCampaignRepository`, and `dunningCommunications` to `createDunningTemplateRepository`.
7. Pass a `UserId` (`usr_...`) as the dunning actor, branch on `schema.invalid_input` from the campaign and segment writes, and on the new results of `handleCommunicationWebhook`. Send provider delivery callbacks as `{ providerMessageId, event, timestamp, metadata }`.
8. Retry a dunning event when its handler throws: the campaign run did not finish.
9. Branch on the new results of the tax repository writes, `deleteJurisdiction`, `generateComplianceReport`, `exportTaxData` and `createAuditEntry`. Pass `taxExemptions` to `new TaxJurisdictionRepository(...)`.
10. Drop the last argument of `new RefundService(...)` and `createRefundService(...)`, and list `createRefundEffects(j, refunds)` in `compose({ effects })` so the rejection mail is sent. Watch dead `refund-approval-request` and `refund-rejection-notice` jobs (`journal.jobs(db, { status: 'dead' })`) and retry them once the mailer works.
11. Branch on `ReferenceNotFound` from the core journal writes (`initiatePayment`, `createSubscription`, `syncSubscription`, `changeSubscriptionPlan`), and on the new results of the `PaymentRepository` writes (`createPlan`, `updatePlan`, `createCustomer`, `updateCustomer`, `deleteCustomer`, `createWebhookEvent`, `updateWebhookEvent`). An HTTP route answers with the failure's `status`.
12. Read the new results of `processDunningEvents` and `previewMultiplePlanChanges`. Listen for `webhook:failed` instead of looking for `Max retry attempts exceeded` in `error_message`.
