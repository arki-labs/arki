# Upgrading queue outcomes

1. Handle the inferred result of each job's `trigger()` and the queue client's
   enqueue operation before using its ID. Return a failure unchanged from
   application helpers. Never put it inside a successful `{ id }` result or
   count it as an accepted job.
2. At an oRPC endpoint, declare `errorMap(...JOB_TRIGGER_FAILURES)` and use
   `orThrowRpc` with that endpoint's error constructors. Flow submissions use
   `FLOW_ENQUEUE_FAILURES`. Validation failures never submit work.
3. Treat `QueueAcceptanceUnknown` as an unknown acknowledgement. Inspect the
   job using its idempotency key before resubmitting. A failed network response
   does not prove that the queue rejected the job.
4. Return domain failures from handlers and middleware. Their definitions remain
   the source of the inferred failure union. Both delivery backends persist a
   refusal as failed work, including its public code and data.
5. Move retry configuration to the job's bounded `retry` backoff. BullMQ's
   `attempts` and `backoff` overrides are no longer the retry policy. Returned
   failures, validation errors and unexpected defects stop by default. Select
   eligible definitions explicitly with `.while(...)`; external effects must
   be safe to repeat. Polling can delay delivery beyond the recorded due time.
6. Honor `ctx.signal`. A handler deadline requests cancellation; it does not
   forcibly interrupt JavaScript. Execution observes the handler's settlement
   before allowing another attempt.
7. Before upgrading an existing runtime-local database, drain its queued work
   under the old version or explicitly migrate/re-enqueue it. New pg-boss
   messages use a versioned input envelope so primitive inputs and trace context
   have an unambiguous stored representation. Old unwrapped rows are not silently
   interpreted as the new protocol.
8. Automatically generated IDs from job triggers and producer enqueue calls are
   now UUID keys on both backends. Treat them as opaque strings. Reusing a
   returned ID as `jobId` suppresses duplicate delivery while the provider retains
   the job, including after restart. Runtime-local maps every key to a queue-scoped
   UUID v5 provider identity and preserves the external key in handler and operator
   views.

Queue Flow remains a dependency tree. Use Journal when a workflow needs persisted
steps, waits, cancellation and restart recovery. Neither queue delivery nor a
flow checkpoint makes an external side effect exactly once.

The application owns OpenTelemetry setup. Queue execution can be observed without
installing an exporter in the library; telemetry failures must not change a job's
outcome.
