# `@arki/auth` security review (W1-09)

Reviewed 2026-10-14 against `better-auth@1.7.7` and `@better-auth/expo@1.7.7` as installed in the workspace.
Better Auth behavior was read from `node_modules/better-auth/dist` (and `@better-auth/core`, `@better-auth/utils`,
`better-call`), not assumed from docs. Paths below are relative to the repo root.

Status key: **pass** = correct today, **fixed** = changed in this review with a test that failed before and passes
after, **deferred** = real gap, owner named.

**Totals: 27 checks: 19 pass, 4 fixed, 4 deferred.**

## Checklist

| # | Check | Status | Evidence | Why it matters |
|---|-------|--------|----------|----------------|
| 1 | Session cookie flags | pass | `node_modules/better-auth/dist/cookies/index.mjs:21` sets `__Secure-` and `Secure` when `baseURL` is `https://`; `:32-38` sets `HttpOnly`, `SameSite=Lax` and `Path=/`. `defineAuthBackend` does not override them (`packages/auth/src/define-auth-backend.ts:209-212`). | Script can't read the cookie, and it never travels over plain HTTP or on cross-site POSTs. |
| 2 | Per-app cookie names | pass | `packages/auth/src/define-auth-backend.ts:176`: `auth-${appKey}` prefix. | Two apps on one parent domain can't read or overwrite each other's session. |
| 3 | Session cookie signature | pass | Signed with the auth secret; checked with WebCrypto `subtle.verify` (`node_modules/better-call/dist/crypto.mjs:11-16`), which compares in constant time. | A changed or forged cookie is rejected, and response timing reveals nothing about the signature. |
| 4 | Trusted origins | pass | The `baseURL` origin is trusted automatically (`node_modules/better-auth/dist/context/helpers.mjs:73-74`). Anything else must be listed in `trustedOrigins` (`packages/auth/src/define-auth-backend.ts:94,217`). Expo adds `exp://` only when `NODE_ENV=development` (`node_modules/@better-auth/expo/dist/index.js:43`). | An unknown site can't make cookie-carrying calls to the auth API. |
| 5 | CSRF | pass | `originCheckMiddleware` checks Origin/Referer on every non-GET request that carries cookies (`node_modules/better-auth/dist/api/middlewares/origin-check.mjs:43-46,96-118`). Magic-link sign-in also checks Fetch Metadata (`:123-140`, used at `plugins/magic-link/index.mjs:73`). `disableCSRFCheck` and `disableOriginCheck` are never set (`context/create-context.mjs:210-211`; `defineAuthBackend` does not expose `advanced`). | A malicious page can't use the user's session to act for them. |
| 6 | Rate limits on sign-in, sign-up, reset and magic link | pass | Turned on when `NODE_ENV=production` (`node_modules/better-auth/dist/context/create-context.mjs:172`). Built-in rules: 3 per 10 s on `/sign-in*`, `/sign-up*` and `/change-password`, and 3 per 60 s on reset and verification email (`api/rate-limiter/index.mjs:305-318`). Magic link: 5 per 60 s on send and verify (`plugins/magic-link/index.mjs:216-222`). | Slows password guessing and stops anyone using the app to send floods of email. |
| 7 | Client IP resolution for those limits | deferred → founder (infra) | With no `trustedProxies`, Better Auth accepts `X-Forwarded-For` only when it holds exactly one address (`node_modules/@better-auth/core/dist/utils/ip.mjs:190`). Otherwise every client shares one bucket per path (`better-auth/dist/api/rate-limiter/index.mjs:242-248`). `defineAuthBackend` gives apps no way to set `advanced.ipAddress`. | Behind two proxies (for example Cloudflare in front of Traefik), all users share 3 sign-ins per 10 s, so one attacker can lock everyone out. The fix depends on the real proxy chain: expose `ipAddress` and set `trustedProxies` for each deployment. |
| 8 | Package helper `ensureRateLimitNotExceeded` | **fixed** | `packages/auth/src/security/rate-limit.ts:26-45`. Before: a limit of N let only N−1 attempts through. The (N+1)th attempt threw the limiter's raw result object instead of `RateLimitExceededError`. A new limiter object was also cached for every caller-supplied key, so memory grew with attacker input. Test: `packages/auth/src/security/rate-limit.test.ts`. | Callers that catch `RateLimitExceededError` returned 500s, and attacker-chosen keys made memory grow without limit. |
| 9 | Timing-safe comparisons | pass | Sign-in with an unknown email still hashes the password (`node_modules/better-auth/dist/api/routes/sign-in.mjs:321-330`). Reset with an unknown email runs a dummy lookup (`api/routes/password.mjs:59-71`). `comparePasswords` uses `bcrypt.compare` (`packages/auth/src/password.ts:21`). Note: scrypt checks its derived key with `===` (`node_modules/@better-auth/utils/dist/password.node.mjs:41`). That key is a salted KDF output, so it can't be attacked byte by byte. `preventTimingAttacks` (`packages/auth/src/security/timing-attacks.ts:21`) adds random delay only and nothing uses it. | Response time doesn't reveal which emails have accounts. |
| 10 | Magic-link TTL and single use | pass | 300 s expiry (`node_modules/better-auth/dist/plugins/magic-link/index.mjs:98`). Tokens are consumed atomically on first verify (`:173`), and `allowedAttempts` is fixed at 1 (`:41-46`). Tokens are 32 random characters. | A leaked or forwarded link is useless after one use or 5 minutes. |
| 11 | Magic-link token at rest | **fixed** | `packages/auth/src/define-auth-backend.ts:189-191` now passes `storeToken: 'hashed'` (Better Auth's default is `'plain'`, `plugins/magic-link/index.mjs:42`). Verify hashes the incoming token before lookup (`:170`), so links in flight keep working. Test: `packages/auth/src/define-auth-backend.test.ts`. | Before, anyone who could read the `verification` table (backup, replica, SQL injection elsewhere) could sign in as any user with a pending link. |
| 12 | OTP | pass (not enabled) | The package registers no `emailOTP` or `twoFactor` plugin (`packages/auth/src/define-auth-backend.ts:182-198`). Apps that add one through `extraPlugins` get Better Auth's limit of 3 per 60 s on OTP send (`api/rate-limiter/index.mjs:314`). | No OTP endpoints exist to attack unless an app adds them. |
| 13 | E2E session handler blocked in production | pass | `packages/auth/src/tanstack-start/e2e-handler.ts:109-111` returns 404 when `NODE_ENV=production`, before reading the body. Every app runner image sets `NODE_ENV=production` (for example `apps/avocabo/start/Dockerfile:124`). Covered by the test "does nothing in production" in `e2e-handler.test.ts`. Caveat: the check fails open if a deployment leaves `NODE_ENV` unset. Check 14 limits the damage in that case. | This endpoint deletes and re-creates accounts, so it must never answer in production. |
| 14 | E2E handler default address allow-list | **fixed** | `packages/auth/src/tanstack-start/e2e-handler.ts:51-52,106,115`. With `allowEmail` omitted, the handler used to accept every address. It now accepts only the reserved `.test` TLD (RFC 2606). All 8 current apps already pass `allowEmail` and use `.test` addresses, so none change behavior. Test: "refuses a real-looking address when allowEmail is omitted". | On any non-production server, a missing option let anyone delete a real person's account and take it over. |
| 15 | Auto email/password only outside production | pass | `packages/auth/src/define-auth-backend.ts:177-180,226-240`. Production apps must pass `emailAndPassword` explicitly, which `src/testing/production-boot.ts` checks. | Test-only password sign-in never appears in production by accident. |
| 16 | Tenant read isolation | pass | `workspaceReadFilter` (`packages/auth/src/workspaces/server/kernel.ts:64-87`): personal rows need `user_id = me`. Org and team rows need `organization_id = activeOrg`, and team rows also need a team the user is on. Covered by the `workspaceReadFilter` tests in `kernel.spec.ts`. | A member of workspace A can't read B's rows through a scoped query. |
| 17 | Tenant write gate | pass | `resolveWriteScope` (`packages/auth/src/workspaces/server/kernel.ts:100-133`) rejects writes into a non-active org (`:111-115`), org-wide writes below `shareRole` (`:117-121`), and teams the user is not on (`:129-131`). Each case has a test in `kernel.spec.ts`. | A member of A can't create rows inside B, or inside a team they are not on. |
| 18 | Scope moves check the row's current scope (fail closed) | **fixed** | `packages/auth/src/workspaces/server/kernel.ts:143-155` (`canSeeRow`), `:177` (`current: RowScope` is now required), `:182-184` (a missing or invisible `current` throws before `applyUpdate`). Before: `reassignScope` checked only the target scope. Its only caller, `apps/avocabo/backend/src/features/workspaces/procedures/move-source-scope.ts:59`, passes no `current`. Tests: the "refuses to move …" cases and "refuses a move when the current scope is missing" in `kernel.spec.ts`. | Without this, anyone who learns a row id can pull another team's, user's or org's row into a scope they can read (an IDOR across workspaces). |
| 19 | Active org re-checked on each request | deferred → follow-up | The kernel trusts `WorkspaceContext.activeOrganizationId` (`packages/auth/src/workspaces/server/types.ts:30-37`). Better Auth clears a session's active org only when the user removes *themselves* (`node_modules/better-auth/dist/plugins/organization/routes/crud-members.mjs:223`). A member removed by an admin keeps `activeOrganizationId` on their open sessions. Today's only consumer re-checks membership (`apps/avocabo/backend/src/features/workspaces/context.ts:63-71`). The package doesn't ship that resolver, so the next app could skip it. | A removed member could keep reading org data until their session expires. Recommend moving `resolveWorkspaceContext` into `@arki/auth/workspaces`. |
| 20 | Role checks in the workspaces plugin | pass | `roleAtLeast` (`packages/auth/src/workspaces/server/types.ts:12-22`) ranks `null` below member, and unknown roles fail the comparison (closed). Org admin endpoints use Better Auth's `hasPermission`. Set-active checks membership (`node_modules/better-auth/dist/plugins/organization/routes/crud-org.mjs:420-425`). | A plain member can't do admin-only sharing, and a bad role string never grants access. |
| 21 | Secret handling | deferred → W1-08 | `packages/auth/src/create-auth.ts:11-13` writes the secret into `process.env.BETTER_AUTH_SECRET` (owned by W1-08). `packages/auth/src/env.ts:32` accepts any non-empty `AUTH_SECRET`; Better Auth only warns below 32 characters (`node_modules/better-auth/dist/context/create-context.mjs:44`). Better Auth refuses its built-in default secret in production (`:42`), and `initAuth` throws when no secret is set (`packages/auth/src/better-auth.config.ts:55-57`). | A weak or leaked secret lets an attacker forge sessions for any user. |
| 22 | Password hashing and length | pass | Better Auth uses scrypt with N=16384, r=16, p=1 and a 16-byte salt (`node_modules/@better-auth/utils/dist/password.node.mjs:3-8,30-33`), and accepts 8 to 128 characters by default. The package helper uses bcrypt cost 12 (`packages/auth/src/password.ts:8`). `PASSWORD_MIN_LENGTH = 8` (`packages/auth/src/constants.ts:9`). | Stolen hashes are expensive to crack. |
| 23 | Redirect and callback URL checks | pass | `callbackURL`, `redirectTo`, `errorCallbackURL` and `newUserCallbackURL` in the body must match a trusted origin or be relative (`node_modules/better-auth/dist/api/middlewares/origin-check.mjs:47-69`). The magic-link verify query parameters get the same check (`plugins/magic-link/index.mjs:134-143`). `createRequireAuth` redirects only to targets the developer sets (`packages/auth/src/tanstack-start/require-auth.ts:27-37`). | A crafted sign-in link can't send the user, or their token, to an attacker's site. |
| 24 | Session expiry and rotation | pass | Sessions last 7 days, and their expiry is pushed forward at most once a day (`node_modules/better-auth/dist/context/create-context.mjs:147-148`). The cookie lifetime matches (`cookies/index.mjs:43`). Every sign-in creates a new session token. | Stolen sessions expire, and an attacker can't plant a session ID before the user signs in. |
| 25 | Account enumeration: sign-in, reset, magic link | pass | Sign-in returns the same `INVALID_EMAIL_OR_PASSWORD` for both cases (`node_modules/better-auth/dist/api/routes/sign-in.mjs:323,330,337`). Reset always answers "If this email exists…" (`api/routes/password.mjs:67-70`). Magic-link send never says whether the account exists; `disableSignUp` refuses only at verify time (`plugins/magic-link/index.mjs:191`). | Attackers can't build a list of registered emails from these endpoints. |
| 26 | Account enumeration: sign-up | deferred → each app | Sign-up returns `USER_ALREADY_EXISTS` unless the app sets `requireEmailVerification` or `autoSignIn: false` (`node_modules/better-auth/dist/api/routes/sign-up.mjs:155,204`). Apps pass their own `emailAndPassword` in production, so each app makes this choice. | Sign-up can show whether an email is registered. Hiding it means a slower sign-up flow, which is a product decision. |
| 27 | Error messages leaking internals | pass | Better Auth returns coded errors. E2E failure bodies exist only outside production (`packages/auth/src/tanstack-start/e2e-handler.ts:148-153`). `WorkspaceScopeError` messages name rules, not data. House-rule note (not a leak): `packages/auth/src/better-auth.config.ts:125,130,142` uses `as any` and `console.error`. | Stack traces and SQL never reach clients. |

## Notes for the founder

- **Needs one app edit (not made here: shared-tree rule):** `current` is now required, so `apps/avocabo/backend` fails typecheck at `src/features/workspaces/procedures/move-source-scope.ts:59` until it passes `current: { userId: source.userId, organizationId: source.organizationId, teamId: source.teamId }` (add `teamId` to the select at `:35-39`). That call site has a real bug today: its `inActiveOrg` check (`:51-56`) lets any org member move a *team* row of a team they are not on, for example to org-wide, which makes it readable. Passing `current` fixes it, and the hand-written check can then be dropped.
- Check 13 relies on `NODE_ENV=production` being set. All runner Dockerfiles set it, and check 14 now limits the damage if one doesn't.
