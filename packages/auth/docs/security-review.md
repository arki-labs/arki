# `@arki/auth` security review

First review: 2026-10-14 (W1-09), against `better-auth@1.7.7` and `@better-auth/expo@1.7.7` as installed in the workspace.
Refreshed: 2026-10-16, for the new API (`defineAuth` + `createAuth`, T10). Better Auth behavior was read from
`node_modules/better-auth/dist` (and `@better-auth/core`, `@better-auth/utils`, `better-call`), not assumed from docs.
Paths are relative to the repo root. Package paths are under `packages/auth/src/`.

Status key: **pass** = correct today; **fixed** = changed with a test that fails without the change; **deferred** = a
real gap, owner named. "Test" names the file that proves the check. A check with no test file is read from code only.

The old API (`defineAuthBackend`, `create-auth.ts`, `better-auth.config.ts`, `tanstack-start/e2e-handler.ts`,
`security/rate-limit.ts`) is deleted. The checks below describe the only API there is.

**Totals: 32 checks: 22 pass, 6 fixed, 3 deferred, 1 removed. 26 of them name a test file.**

Test: `pg/security/rate-limit.test.ts` (4th sign-in in 10 s is 429; two instances share one budget). | Slows password guessing on every replica at once.                                                   |
| 7   | Client IP resolution for those limits                 | **fixed** (configurable) | `runtime().clientIp.header` becomes `advanced.ipAddress.ipAddressHeaders` (`pg/assemble.ts`). The header each deployment must name (for example `cf-connecting-ip` behind Cloudflare and Traefik) is a deployment fact, not in the repo. Without it (fixed 2026-11-01), no header is trusted: the engine reads only `x-arki-auth-client-key`, which the handler fills and never takes from the caller: the runtime's socket address (`request.ip`), else the target account (signed-in user, else an allowlisted body `email`, as a derived `fd00::/8` address), else one shared key. The body `email` counts only on `/sign-in/email`, `/request-password-reset` and `/sign-in/magic-link`, and a signed-in user's id wins over it. Production refuses to boot without `clientIp` (`ARKI_AUTH_E009`, every method); `clientIp: { from: 'socket' }` names the socket and refuses a production request without one (`ARKI_AUTH_E010`). Before, the engine fell back to the caller-set `x-forwarded-for`, and a fresh value bought a fresh budget. Tests: "without clientIp.header …" and "refuses to boot in production without clientIp" in `pg/security/rate-limit.test.ts`, and `pg/id-token.test.ts`.                                                                                                                          | Without it, all users can share one bucket, and one attacker can lock everyone out.                 |

## Notes for the founder

- Check 7 needs one fact per deployment: the header the ingress sets to the client address. Set it in each app's
  `runtime().clientIp`.
- Check 29 is the open fail-closed gap. The fix is a strict option in `@arki/kv` that throws when Redis is not ready,
  used by `pg/security/kv-storage.ts`.
- Check 19 stays open: ship a membership resolver in `@arki/auth/pg/workspaces` so the next app can't skip it.
