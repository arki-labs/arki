# Upgrade @arki/auth 0.5.0 to 0.6.0

You must act only if you match `AUTH_FAILURES` codes one by one with an exhaustive switch, or if your app counts on a re-sign-in keeping the old session of the same user; everyone else can upgrade with no change and adopt fresh sessions or passkeys when they want them.

## What changed

- Add a fresh-session check for risky actions. `sessions.freshFor` (seconds) in `defineAuth` sets how long a session counts as fresh after sign-in; the engine's delete-account, unlink-account and list-sessions routes follow it too (unset: the engine's default of 1 day). The new `freshSession` step is used like `authed`: a guest gets `auth.unauthenticated`, an older session gets the new `SessionNotFresh` failure (`auth.session_not_fresh`, 403, data `{ freshFor }`), part of `AUTH_FAILURES`. A sign-in that succeeds on a request carrying the same user's session now revokes that session, so a re-check leaves one session. The principal carries `freshFor` when it is set.
- Add passkey sign-in. List `'passkey'` in `defineAuth({ methods })` with `passkey: { rpName }` (required with the method, refused without it); the relying party id and the expected origin come from `runtime.url`. Build the table with the new `createPasskeyTables(c, { fill, user, ids })` from `@arki/auth/pg` and `@arki/auth/sqlite`, and pass it with the other tables; boot refuses `passkey` without it (`ARKI_AUTH_E007`). `authIdSources` gains `passkey`, and `passkeyIdColumns`, `PasskeyId`, `createPasskeyId` and `passkeyIdSchema` are new. The client from `createAuthClient` gains `signIn.passkey`, `passkey.addPasskey`, `passkey.listUserPasskeys` and `passkey.deletePasskey`, typed from the definition, and `capabilities.passkey`. A passkey sign-in counts as a fresh sign-in for `freshSession`, and one made on a request with the same user's session replaces that session.

   ```ts skip="before: the 0.5.0 failure set"
   switch (failure.code) {
     case 'auth.unauthenticated':
       return showSignIn();
     // ...the other AUTH_FAILURES codes
   }
   ```

   After:

   ```ts skip="the 0.6.0 failure set; the example shows one branch"
   switch (failure.code) {
     case 'auth.unauthenticated':
     case 'auth.session_not_fresh':
       return showSignIn();
     // ...the other AUTH_FAILURES codes
   }
   ```

2. Check any flow that signs a user in again while they are signed in. A successful sign-in on a request that carries the same user's session now revokes that session, so the user is left with one session. A cookie or token you kept from the old session stops working. Another user's sign-in keeps the old session.

3. Optional: guard risky actions with a fresh sign-in. Set `sessions.freshFor` (seconds) and use `freshSession` where you used `authed`.


   After:

   ```ts skip="the 0.6.0 API; see the README section on fresh sessions for the full setup"
   const auth = defineAuth({ methods: ['email'], sessions: { freshFor: 30 * 60 } });
   ```
