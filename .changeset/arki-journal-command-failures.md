A command can say no by returning a failure from `@arki/failure` instead of throwing a `CommandError`. The journal ships four, each with data `{ detail }`, the message for the client: `CommandNotFound` (`journal.not_found`, 404), `CommandInvalid` (`journal.invalid`, 400), `CommandForbidden` (`journal.forbidden`, 403) and `CommandConflict` (`journal.conflict`, 409), exported from `@arki/journal` and `@arki/journal/errors`. An app's own `defineFailure` values work the same way. When a command handler, its `authorize` or an `events` function returns a failure, the command's transaction rolls back exactly as for a throw, and `journal.run` returns the same failure instance. The type is inferred: `run` returns `Result | Failure` from the handler, and the failures `authorize` can return are added to the command's type. An `events` failure rolls back the write's savepoint and comes back from `write` (now `WriteResult | Failure`); the handler returns it on. A child command's failure comes back from `context.run` with its savepoint rolled back. A failure is never stored as an idempotency receipt, so a repeat runs again. Once a write's `events` or a child command returned a failure, the command must end with a failure (that one or another): a handler that still returns a success makes the run throw the new `JournalError` code `IGNORED_FAILURE`, naming the write or child and the failure code, and nothing commits. An effect that ignores a failure from `ctx.run` and returns a success fails its job with that failure, dead after one try. `@arki/journal/orpc`: `toORPCError` turns a failure into the `ORPCError` with its code, status, message and data, and `commandErrors()` also answers a failure the procedure returns as an error. A contract-first procedure uses `orThrowRpc` and `errorMap` from `@arki/failure/orpc` for typed client errors. `CommandError` and `isCommandError` still work.
