Three fixes. (1) `DunningCampaignService.updateCampaign` takes optional `templates`, the same step shape and rules as create (at least one step, unique step numbers). The steps become exactly that set, in one transaction: a step with the same `stepNumber` is updated in place (its id and history stay), a new number is added, a missing number is deleted. `updateDunningCampaignInputSchema` gains `templates`; create and update share `dunningCampaignTemplatesSchema`, and create now also rejects duplicate step numbers. (2) New `SubscriptionManager.setCancelAtPeriodEnd(subscriptionId, flag)` sets or clears cancel-at-period-end with the provider and stores it through the new `setSubscriptionCancelAtPeriodEnd` journal command (event `SubscriptionCancelAtPeriodEndSet`). `SubscriptionManager.updateSubscription` now stores the new plan (new `changeSubscriptionPlan` command, event `SubscriptionPlanChanged`); before, the provider changed but the row kept the old plan. `CoreWrites` gains both commands. `updateSubscriptionInputSchema` now requires a `planId` or a `cancelAtPeriodEnd`. (3) `customers_provider_customer_id_idx` is unique on `(provider, provider_customer_id)` instead of `provider_customer_id` alone, so two providers may use the same id. Apps that already applied the old index must drop it and create the new one.
